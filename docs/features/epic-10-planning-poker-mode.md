# Эпик 10: Planning Poker Mode (Quick Sessions)

> **Статус: Phase 2 завершена. Эпик закрыт.** Все P0/P1 stories реализованы (10.1, 10.2, 10.3, 10.4, 10.5, 10.7, 10.8). Дополнительно доставлены: QR-код для шеринга, leave room для гостей, action для kick (UI добавим если будет фидбэк), cron-cleanup истёкших данных, governance (Terms / Privacy / Cookies + consent UX), редизайн landing с двумя равными CTA, error pages 404/500. Story 10.6 (история раундов в сайдбаре) и 10.9 (тогл «только авторизованные») — отложены как nice-to-have, продукт работает без них.

## Бизнес-цель

Дать командам возможность быстро провести planning poker без полного цикла настройки проекта (спринты, Гант, тикеты с названиями, регистрация всех участников). Целевой сценарий — корпоративный планинг, где названия и ID тикетов нельзя вводить во внешний инструмент (NDA, политика DLP, закрытая Jira), но команде нужен совместный механизм голосования. Дополнительно эпик вводит **выбор метода эстимации** на уровне проекта — текущий 4-факторный, классический Fibonacci, часы или дни — что закрывает потребности команд, не работающих в Story Points.

## Целевой пользователь и сценарий

**Job-to-be-done:** «Я хочу за минуту собрать команду в общую комнату, ввести в неё минимум данных (или ничего) и провести покер по N задачам, не утечкая названия тикетов в стороннее приложение».

**Ожидаемый Time-To-First-Vote** для команды из 6 человек: **под 60 секунд** от открытия ссылки до голосования первого раунда (сейчас — 5+ минут с регистрацией, созданием проекта, инвайтами и созданием тикета).

## Что планируется реализовать

### Story 10.1: Точка входа «Planning Poker» в меню
- Новая вкладка в основной навигации (рядом с «Projects»): `Planning Poker`.
- Страница `/planning-poker` — список активных Quick-комнат пользователя + CTA «New Room».
- Quick-комната под капотом — это `Project` с флагом `isQuick=true` и `expiresAt`. Это позволяет переиспользовать `ProjectMember`, `Vote`, `EstimationSession`, polling и UI-компоненты эстимейта.

### Story 10.2: Гостевой вход по нику
- Если приглашённый не авторизован, он попадает на форму «введи ник».
- Создаётся `User` с `isGuest=true`, `passwordHash=null`, `expiresAt` = TTL комнаты.
- Гость автоматически становится `ProjectMember` Quick-комнаты с ролью `null`.
- Авторизованные пользователи используют существующий аккаунт.
- Cleanup истёкших гостевых юзеров и Quick-комнат — лениво при чтении или через cron (TBD на этапе реализации).

### Story 10.3: Раунд без названия задачи
- В Quick-режиме `Ticket.title` не требуется. Тикет создаётся автоматически с именем вида `Раунд N` (счётчик в рамках комнаты).
- В UI комнаты нет полей «название», «AC», «URL», «описание» — только кнопка «New Round», которая сразу запускает голосование.
- Опционально хост может задать **локальную** метку раунда (хранится только в браузере хоста, в БД не уходит) — для собственной навигации между раундами, если их много.

### Story 10.4: Мульти-методное голосование
- Новое поле `Project.estimationMethod: EstimationMethod` определяет метод:
  - `COMPOSITE_SP` — текущий 4-факторный (Dev Effort / QA Effort / Risk / Uncertainty → медиана → SP)
  - `FIBONACCI_SP` — одно число из шкалы `1, 2, 3, 5, 8, 13, 21, ?, ☕`
  - `HOURS` — одно число в часах
  - `DAYS` — одно число в днях
- Vote расширяется полем `singleValue: Float?`. Существующие 4 поля становятся nullable.
- Логика рендера `VotingForm` ветвится по методу: для `COMPOSITE_SP` остаётся текущая форма с 4 ползунками, для остальных — одна линейка карточек со шкалой метода.

### Story 10.5: Reveal с медианой и round-up рекомендацией
- `COMPOSITE_SP` — без изменений (медианы по 4 критериям, конвертер SP, пропорция Dev/QA).
- `FIBONACCI_SP` — медиана `singleValue` + разброс (min/max) + список голосов.
- `HOURS` / `DAYS` — медиана + **round-up** к ближайшему большему значению из sane-шкалы:
  - Шкала `HOURS`: `1, 2, 4, 8, 16, 24, 40` (захардкожена в MVP)
  - Шкала `DAYS`: `0.5, 1, 2, 3, 5, 8, 13` (захардкожена в MVP)
  - Round-up выбран намеренно: задачи в реальности чаще длятся дольше медианы, чем короче — буфер безопаснее оптимистичной оценки.
- Для `HOURS` рядом с рекомендацией отображается перевод в дни через `Project.workingHoursPerDay` (новое поле, дефолт 8).

### Story 10.6: История раундов в комнате
- Сайдбар комнаты показывает список всех раундов сессии (`Раунд 1: 5 SP`, `Раунд 2: 3 SP`, `Раунд 3: 16h`...).
- Клик на раунд открывает модал со статистикой голосов (переиспользуется существующий `ticket-stats` API + модал из Story 2.4).
- История живёт в рамках комнаты, истекает вместе с ней по TTL.

### Story 10.7: Метод эстимации в настройках обычного проекта
- В `/project/[id]/settings` добавляется секция «Метод эстимации» с дропдауном из 4 значений.
- Изменение метода не влияет на уже принятые оценки (исторические `Vote` остаются как есть).
- Дефолт для существующих проектов — `COMPOSITE_SP` (обратная совместимость).
- Дефолт для новых Quick-комнат — `FIBONACCI_SP`.

### Story 10.8: Метод эстимации в Quick-комнате
- Хост Quick-комнаты может сменить метод в любой момент через настройки комнаты.
- Изменение метода между раундами разрешено: каждый раунд может быть в своём методе (метод фиксируется на уровне раунда/тикета, не сессии).

### Story 10.9: Опция «Только авторизованные»
- Тогл в настройках Quick-комнаты, по умолчанию выключен.
- Если включён — guest-join формы нет, неавторизованный пользователь редиректится на `/login` с redirect-параметром.
- Нужен для команд с жёсткой политикой по неперсонифицированному доступу.

## Архитектурные решения

| Решение | Обоснование |
|---|---|
| Quick-комната = `Project` с флагом `isQuick=true`, а не отдельная модель | Переиспользуем `ProjectMember`, `Vote`, `EstimationSession`, polling, UI. Phase 3 (мост «сохранить в обычный проект») становится сменой флага вместо миграции данных. |
| Гость = `User` с `isGuest=true` и `expiresAt`, а не отдельная модель | Переиспользуем `ProjectMember`, авторские поля, авторизационные хуки. |
| `Vote.singleValue` + 4 nullable поля в одной таблице, не разные таблицы по методу | Простота. Метод хранится на уровне `Ticket` (или `EstimationSession`), при чтении знаем, какие поля интерпретировать. |
| Шкалы округления захардкожены в MVP | В Phase 2 — настраиваемые как `SpScaleItem`. Сейчас не блокирует ценность, а конфигурируемость требует UI/миграций. |
| Round-up к sane-значению, не round-nearest | Эмпирически задачи дольше медианы чаще. Если команда хочет round-nearest — решим по фидбэку. |
| TTL Quick-комнаты — 24 часа (черновой дефолт) | Конкретное значение — на этапе реализации. |
| Cleanup истёкших Quick-комнат и гостевых юзеров — **lazy** (проверка `expiresAt` при чтении / попытке входа) | Дешевле для MVP, не требует инфраструктуры под cron. При росте объёмов или появлении необходимости в фоновой очистке — пересмотр на cron (см. Phase 2+). |

## Метрики успеха

| Метрика | Цель |
|---|---|
| Time-To-First-Vote (новая команда из 6 человек, открытая ссылка) | < 60 секунд |
| Drop-off на входе в Quick-комнату (гость не дошёл до голосования) | < 10% |
| Среднее число раундов за сессию (показатель реального использования, не «потыкали») | > 2 |
| Возвратность хоста (создал >= 2 комнаты за месяц) | > 30% |
| % проектов, переключивших метод с `COMPOSITE_SP` (отдельная метрика для Story 10.7) | трекинг, без цели — индикатор PMF другого метода |

## Phase 2+ (вне MVP)

- Настраиваемые шкалы для `HOURS`/`DAYS` (аналог `SpScaleItem`).
- Переход с lazy-cleanup истёкших Quick-комнат и гостей на cron-задачу (если lazy перестанет справляться по объёму или появятся side-эффекты от «зависших» записей).
- Round-up vs round-nearest как настройка per project.
- Мост «сохранить Quick-сессию в обычный проект» — конвертация раундов в полноценные тикеты с привязкой к спринту.
- QR-код для шеринга комнаты в офисных митингах.
- Кикнуть гостя (host-only).
- Локальные метки раундов с синхронизацией (опционально, сейчас локально в браузере хоста).
- Экспорт лога раундов (CSV/PDF) — без названий задач, только нумерация и итоги.
